→ receipt → publish → 等 `required`；加 `--merge` 才 queue、等合併、`cleanup-merged`、`sync-main`。`--merge` 在 queue 前先等 PR exact head 上的 `agent-review` 收斂（讀該 SHA 全部同名 check run：Actions job 未完成或尚無結論即等待，被取消 run 遺留的 in_progress verdict marker 不算；只採「屬於本 PR」的 run——由 marker／details_url 取 workflow run id，讀 `actions/runs/<id>` 的 `pull_requests[].number`，其為空才退而比對 `head_branch` 是否等於本 PR head ref，無法歸屬（run 讀不到、comment 並列出每則 `path:line`、標題與連結；只有 `--accept-review-findings '<reason>'` 能放行，理由寫進 log 與結果的 `review` 欄位；`neutral` 不是 verdict（只代表 workflow 等 bot 20×15s 後放棄，bot 常在之後才審、下一個 run 才貼真正結論），所以只有 success／failure 結束等待；到 `--timeout` 仍只有 `neutral` 就拒絕 queue，只有 `--accept-no-review '<reason>'` 能放行，且 PR 上必須已有 maintainer 留下、點名 exact head 的 `CR verdict: APPROVE <sha>`（見 `docs/sop/review_discipline.md`；理由寫進 log 與 [--lane <新 lane>] --check … [--merge]`（delivery 選項必須放在 `redeliver` 之後；放在前面會以 usage error（exit 2）拒絕，不會被默默忽略）：修正須在新 branch；舊 lane 仍持有 Scope，所以在新 lane claim 前以 `worktree_orchestrate.py resolve --status abandoned` 退役，`--expected-generation`／`--expected-head-sha` 每次直接讀 registry 的 `claim_generation`／`handed_back_sha`；新 PR 建立後才以附新 PR 連結的 comment 關閉舊 PR（因此 redeliver 的 `delivery.py publish` 帶 `--replaces-pr <舊 PR>`，只把該 PR 從 publish preflight 的 Scope collision 比對中排除，其他 open PR 與 registry 盤點照常擋）（此時重讀發現舊 PR 已 MERGED 就中止：不關閉、不刪舊 remote branch，錯誤指出新 PR 已發布）；舊 remote branch 只在仍等於 published head 時以 `--force-with-lease` CAS 刪除，被推動過就保留並回報。各步驟重讀事實，重跑即續做；新 worktree 已被 publish 移除時加 `--new-branch <新 branch>` 續跑。不用 `delivery.py abandon-pr`：它拒絕 head 已移動的 PR，且在替代 PR 存在前就關閉；但保留它的拒絕條件：舊 PR 帶 hard hold（`delivery-hold:p0/p1/security` label 或 typed／legacy body hold；關閉會把 hold 洗掉，須先 `delivery.py reconcile-holds`）或已開 auto-merge／在 merge queue 中，就在任何 mutation 前拒絕，並在 abandon 舊 lane 與關閉舊 PR 前各重讀一次（中間的 `--check` 可能跑好幾分鐘）；abandon 撞上 operation lock 時，每次等待後、重試前也重讀一次，新出現 hold 或 queue 就中止、不 abandon。redeliver 另在任何 mutation 前要求新 tip 承接舊 lane：tip 含 registry 記錄的 `handed_back_sha`（`git merge-base --is-ancestor`），或舊 lane 加入的每個 commit 在新 tip 都有 patch-equivalent（`git cherry`，即未改內容的 rebase）；無關 branch、改寫過內容的 commit 或本機沒有該 hand-back 物件一律拒絕並列出對不上的 commit，不 abandon、不關 PR、不刪 branch。hand-back 的 outcomes 只來自本次實際執行的 `--check`（exit code＋stdout 最後一個非空行，stdout 為空才取 stderr），無法手填；check 失敗時 stderr 印出該 check 輸出的最後 40 行，每個 check 的完整輸出另存 canonical checkout 的 `.cache/deliver-checks/<branch>-<label>-<UTC 時間>.log`（gitignored；失敗 JSON 的 `checks[].log` 給路徑，路徑不進 sealed outcomes）；check 失敗、髒樹、main 分支、無法乾淨 rebase 皆在 claim 前拒絕。任一階段失敗時錯誤全文輸出、不截尾：`delivery.py` 的 `ok:false` JSON 取整段 `error`（底層 GitHub 訊息常接在很長的 GraphQL query 之後），其他命令輸出完整 stderr／stdout。delivery／registry／worktree mutation 撞上 `delivery mutation already in progress`（operation lock 在任何變更前取得，被拒的嘗試什麼都沒做）時，每 5 秒重試並印出持有者，最多 `--lock-timeout` 秒（預設 600），逾時才以完整錯誤失敗；其他失敗不重試。環境變數 `KG_DELIVERY_LOCK_WAIT_SECONDS=N` 覆寫 `OperationLock` 每次取鎖的有界等待（未設定預設 30 秒；`0`／負值／無法解析為 fail-fast；`cleanup-merged` 預設 120 秒；`KG_DELIVERY_LOCK_DIR` 測試 hook 存在且未設此變數時其餘命令預設為 fail-fast，詳見 `docs/sop/delivery_control_dogfood.md`），與此 5 秒重試疊加。`deliver.py gc [--dry-run]` 以一次 REST（`gh api --paginate --slurp repos/{repo}/pulls?state=closed`，不耗 GraphQL 額度）取得 head branch → 已 merged PR，對每個仍持有 Scope 的 lane（`active`／`published`／`cleanup_pending`，不論 worktree 是否還在）、其 hand-back SHA（無則 worktree HEAD）等於或為該 PR head 祖先者跑 `cleanup-merged`（即 doctor 報的 ghost claim）；HEAD 不被該 PR 涵蓋者保留並列在 `kept`。Scope 一律由 worktree 對 `origin/main` 的 diff 推得（`worktree_orchestrate.py adopt --scope-from-diff` 同理；`deliver.py --scope-from-diff` 另會在 hand-back 前刷新已 adopt 的 active claim 的 Scope）；adopt 宣告的 base 一律是 exact `git merge-base HEAD origin/main` SHA（不是 40-hex 即在 adopt 前失敗），從不傳 symbolic `origin/main`：adopt 實際執行時才解析 ref，等 operation lock 期間別的 delivery fetch 推進的 main 不在 HEAD 內，hand-back 會以 declared base 非 HEAD 祖先拒絕；若既有 active claim 的 `base_sha` 不是分支與 `origin/main` 的 fork point（舊的本機 `main`），會以 `worktree_orchestrate.py readopt` 在同一 operation lock lease 內原子地退役並重新 adopt（中間不會被重疊 Scope 的 `open` 搶走）；`--branch` 續跑遇 PR 已 merged 且無待清理 claim 時直接停止並要求從 `origin/main` 開新 lane。preflight 的 `git fetch origin main` 在 operation lease 內執行（fetch 改寫所有 worktree 共用的 `refs/remotes/origin/main`，並行 fetch 實測會以 `cannot lock ref … is at X but expected Y` 失敗），lease 忙碌時同樣每 5 秒重試、受 `--lock-timeout` 約束。`cleanup_pending` 且 PR 已 MERGED（head 為預期 HEAD；或 remote branch 已消失且從無任何 PR 紀錄，CLOSED-unmerged 須走 closed-PR disposition）的 lane，可用 `worktree_orchestrate.py resolve --status abandoned` 退役，證據由指令自行查證；registry CLI 本身不接受退役證據參數，只有 orchestrator 驗證後以 in-process 傳入。測試在 `delivery-control` 群組（`ops/tests/test_delivery_deliver.py`）。
- Release preflight：`ops/release_train.py`（唯讀，`--json`；exit 0/1/2＝ready/warn/blocked，`--skip-remote` 不 ssh felix）回答「現在能不能推 origin/prod」，每項檢查對應一次真實踩坑：main 紅燈／未同步、`origin/prod` 不能 ff（reconciler 用 `--ff-only`）、release 必碰的 `backend/src/kg/api.py` 未格式化（PR gate 只格式化變更檔，candidate PR 會紅）、felix `~/kg-prod` 與 `origin/prod` diverged（歷史被改寫，ff-only 會拒絕部署）、reconciler dry-run／launchd 狀態、live 版本是否已在上次 release、24h 內備份、production env、範圍內的 auth／billing／LLM／handler 檔案（出貨需 owner 明確同意）。測試在 `doctor` 群組（`ops/tests/test_release_train.py`）。
- Complexity budget：`ops/complexity.py`（`check`／`ratchet`／`show`）以 `ops/complexity_budget.json` 的行數上限（只算 `.py/.sh/.md/.yml/.yaml/.swift` 等人寫的程式碼與文件，fixture、plist 等資料檔不算，重新產生資料不得讓閘門變紅）約束 `ops/`、`docs/`、`.github/workflows/` 不會無聲膨脹（並回報 ops:ios 比值，目前約 1.2＝工具行數仍大於產品行數）。`ops/tests/test_complexity.py::test_the_repository_is_within_its_complexity_budget` 在 `doctor` 群組內經 `complexity.main(["check", *ci_args()])`（與操作者同一入口）執行：lane（HEAD 不等於 `origin/main`）只為自己的成長付費：每區 delta = 現在行數 − merge-base（`origin/main`，否則 `main`）行數（兩邊用同一個 `count_lines` 規則），delta ≤ 該 lane 的 headroom 即過，或 lane 自行在 `ops/complexity_budget.json` 提高 ceiling 並寫明理由（此時改以新 ceiling 做絕對判斷）；delta 超過才紅。headroom = 當前 merge-base 的 headroom 與 lane「原始 fork point」的 headroom 取大者（ceiling 取自各自 commit 的 budget 檔）：`ops/deliver.py` 會在檢查前把 lane rebase 到 `origin/main`，merge-base 因而變成 main tip，所以原始 fork 取 `KG_COMPLEXITY_FORK_BASE`（若設），否則本機 branch reflog 的建立 commit；CI 的 merge commit（HEAD＝main＋PR）則取 PR 自己的 fork point；都沒有時退回當前 merge-base。如此互為兄弟、各自在原始 headroom 內的 lane 不論誰先合併、是否 rebase 都會過；樹的絕對行數超過 ceiling 但 lane 自身成長仍在額度內時只印 WARNING（main 超標，需另開 rebaseline PR），不擋 lane。HEAD 即 main 本身、或加 `--absolute`／`--strict`（push 到 main，`GITHUB_EVENT_NAME=push`，由 `ci_args` 自動加；doctor 亦走絕對）時，絕對超標仍是失敗，紅 trunk 保持可見；push `--strict` 轉紅時 rebaseline PR 是緊急事項，因為此後所有 lane 的 headroom 都被夾到 0。`--base REF` 覆寫 base；找不到 merge-base、base 讀不到或其物件缺漏時印 stderr 理由並退回絕對判斷。`slack` 只是 ratchet 的重設餘量，不參與 gate。超標即紅時，解法只有兩種且都留在 PR 內可審視：刪掉東西，或在同一 PR 提高 ceiling 並寫明理由。`ratchet` 只會把 ceiling 往下收（刪除的額度入帳、不可被再次無聲花掉），`doctor.py` 另顯示 headroom 最小的區域。
